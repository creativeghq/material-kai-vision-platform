Construction · Requests — RFIs & Submittals

/projects/:id?tab=requests

The Requests register is one threaded place for everything that needs an answer or a decision on a job — client questions and change requests, and the two team-facing contract instruments: RFIs (requests for information) and submittals (materials/shop-drawings sent for approval). RFIs and submittals are numbered and due-dated, can cite the exact drawing they're about, and the register warns you if the same question has already been asked.

Where: a project → the Client stage → the Requests section (?tab=requests). A notification link opens the exact thread. RFIs and submittals are internal/team-facing by default; client-facing kinds can be shown to the client.

Kinds & numbering

A request is one of: question, change request, approval request, info request, RFI, or submittal. The last two are team-facing, so they're numbered — a reference like RFI-003 is assigned by the platform when you raise it (client-facing kinds get no number). The number is stated as being assigned on raise, so you never pick it yourself.

Raising an RFI

  1. Raise request → set the title, details and type.
  2. Optionally pick which drawing it's about — the picker lists every revision, each tagged (current) or — superseded, because on site people often hold the wrong sheet.
  3. For a team-facing kind, set Answer needed by. Raise it — the reference is assigned.

“Has this already been asked?” As you type the title, the register quietly searches for similar existing requests and shows an advisory panel — reference, title, status, and for a resolved one the last answer inline. It never blocks you (dismiss it with “mine is a different question”), and naming a drawing widens the search rather than narrowing it. It's there to stop the same RFI being raised twice.

Tracking answers & due dates

Each request is a thread. An owner's reply flips it from open to answered; statuses run open → answered → resolved (or won't do). An overdue open request shows “Answer was needed by …” in red. A request that cites a drawing shows an amber warning if that sheet has since been superseded — so an answer is never read against the wrong revision. Closed requests are hidden unless you tick Show closed.

Submittals — closed by a verdict

A submittal isn't closed with the ordinary status dropdown — you record a verdict: Approved, Approved as noted, Revise & resubmit, or Rejected. Revise & resubmit deliberately reopens the submittal and bumps its revision rather than closing it, so the back-and-forth is tracked properly. (Approval requests get a simple Approve / Decline.)

Worked example. A dimension on the current architectural sheet doesn't work. From the drawing markup you cloud it and Raise as RFI — it lands here as RFI-004, tied to that revision, with an answer-by date. If someone had already asked it, the dedup panel shows their thread and its answer, so you close yours as a duplicate instead of chasing it again.

From chat: the Requests register is a UI tool — the assistant doesn't raise or answer RFIs.
