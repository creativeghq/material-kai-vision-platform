# Storage Buckets

> Extracted from CLAUDE.md 2026-07-29 during the instructions/history split. This is the reference detail; CLAUDE.md keeps only the routing rule.

The platform uses **8 buckets** (down from 17). Routing is path-based; feature identity lives in the top-level folder, not the bucket name. (Count corrected 2026-08-07: `property-media` and `documentation` existed live but were missing from this table.)

| Bucket | Public | Folders / use |
|---|---|---|
| `pdf-documents` | 🔒 private (signed URLs) | KB raw PDFs at `{user_id}/...` · `catalog-source/{catalog_id}/...` · `catalog-output/{catalog_id}/...` · `quote-output/{quote_id}/...` · `moodboard-output/{moodboard_id}/sheet-{sheet_id}.pdf` · `client-view-output/{project_id}/cv-{client_view_id}.pdf` |
| `pdf-tiles` | ✅ public read (bucket `public=true`) | `extracted/{document_id}/...` (KB) · `catalog-extracted/{source_pdf_id}/page-NNNN-{bbox}.png` |
| `generation-images` | ✅ public, 100 MB, image/video/model | `{user_id}/...`, `gemini/`, `videos/`, `user-uploads/`, `social/`, `product-crops/...` (SAM crops + segmentation), `agent/` (chat uploads), `3d/{product_id}/` (product 3D models — glb/gltf/usdz, rows in `product_3d_models`, written by `product3dService`; MIME allowlist includes `model/gltf-binary`, `model/gltf+json`, `model/vnd.usdz+zip` since 2026-08-07), `designer/` (designer module) |
| `quote-templates` | 🔒 private, 50 MB | Quote template PNGs at root (`template-cover.png`, `template-content.png`, `template-backcover.png`, `template-intro.png`) · `catalog/cover.png` / `catalog/backcover.png` (catalog templates) |
| `moodboard-sheet-references` | ✅ public | Static admin-curated illustrations for the sheet-type picker (`material_board.png`, `color_palette.png`, etc.) |
| `profile-avatars` | ✅ public, 2 MB | `{user_id}/avatar.ext` |
| `property-media` | 🔒 private, 50 MB (signed URLs, 1h) | Real-estate listing photos/videos/PDFs — `real-estate-api`/`real-estate-feed`/`real-estate-public`, `PropertyWorkbench`. Reference-set rows come from `property_documents` + `property_photos` |
| `documentation` | ✅ public, 25 MB, images | Screenshots for the public documentation pages (`public/documentation`) |

**Privacy model:**
- `pdf-documents` is private — every reader mints a fresh signed URL via `createSignedUrl()`. Stop persisting full URLs in DB rows; store the storage path (`storage_bucket` + `storage_object_path`) and re-derive on each render. The 2026-05-23 audit hardened both write side (upload routers no longer persist `file_url` in metadata; resume reads `storage_bucket`/`storage_object_path` and signs fresh) and read side (`KnowledgeBasePDFViewer.handleOpenOriginalPdf` calls `createSignedUrl` on demand instead of opening a stale persisted URL).
- `pdf-tiles` is a **public-read** bucket (`storage.buckets.public=true`, verified 2026-06-21) — object GETs via the `/object/public/pdf-tiles/...` URL succeed for anon (extracted tile/crop images are not sensitive). Earlier docs claiming "authenticated-only read" were wrong. Writes are service-role. (This is what lets the public KB / brand pages show product thumbnails to logged-out visitors.)
- `generation-images` is public-readable but writes are RLS-gated to authenticated users or service role.
- `quote-templates` is admin-only RW via the `quote_templates_admin_all` policy (admin / super_admin / owner roles, plus service_role).

**Cleanup wiring:**
- `storage-orphan-cleanup-cron` scans `pdf-documents` (72h grace) + `pdf-tiles` (48h grace) + `generation-images` (14d grace). Grace bumps landed 2026-05-23 to widen absorption for delayed-DB-write paths (admin uploads, schedulers that upload to storage minutes before inserting the documents row, background catalog-restore). Each `batch.remove()` is preceded by a `verify_storage_orphans(bucket, paths[])` call that re-checks the candidate batch against the live DB reference set — closes the race between `find_orphan_storage_objects` snapshot time and the actual delete (a 5000-path batch can take ~30s, and a DB ref written in that window would otherwise be left dangling). Race-protected skips are counted in `storage_cleanup_log.details.skipped_raced`. Fail-closed on verify error — a failing RPC skips the batch rather than blindly delete the stale snapshot.
- **Entity-delete storage cleanup is GC-based, NOT trigger-based (corrected 2026-06-22).** There are **no** `_cleanup_*_storage` AFTER DELETE triggers — earlier docs/comments claiming "7 AFTER DELETE trigger functions" were inaccurate; those triggers never existed in the live DB (and a SQL trigger deleting `storage.objects` rows would orphan the physical blob anyway — only the Storage API removes both). Instead, deleting a moodboard / agent chat / quote / sheet / client-view removes the row(s) (FK CASCADE handles children), which drops the file out of `build_storage_reference_set()`, and **`storage-orphan-cleanup-cron` garbage-collects the now-unreferenced files** via `find_orphan_storage_objects()` (grace windows above). `build_storage_reference_set()` is the live-reference set the cron diffs against (protects in-use files + per-live-conversation/inbox prefixes); it is a plain function, NOT a trigger. The sheet (`moodboardSheetsService`) and client-view (`clientViewsService`) services additionally do a best-effort client-side `storage.remove()` of their PDF before deleting the row so it's freed immediately; the cron is the backstop.
- `reset-platform` clears `pdf-tiles` + `generation-images` only. KB raw + generated outputs in `pdf-documents` survive a reset (the orphan cron picks up any that the table-clear step orphans).
- **A table holding a storage path MUST have a branch in `build_storage_reference_set()`, and this is now enforced.** Seven did not (2026-08-04). `public.payments` was a live loss — its receipt PDFs go to `pdf-documents` on a 72h grace, and **both** on this project had already been deleted while the rows still held the path. `hr_documents`, `hr_accounting_documents`, `material_images`, `property_documents`, `property_photos` were latent (empty). All registered; `public.uploaded_files` is deliberately excluded (admin test scaffolding, and its `storage_path` holds a URL, not an object path). The guard is the `ops.storage_paths_unregistered` probe, which reads the function's own body so it cannot drift from what the cron honours — see [prevention-coverage.md](prevention-coverage.md) shape 4d.
- **A storage URL is a storage reference too, and the probe could not see one (2026-08-30).** `ops.storage_paths_unregistered` only ever considered columns NAMED `%storage_path%`, so two tables holding a URL were invisible to it: `generation_3d` — where every AI image this platform generates is recorded, as `models_results -> <model> -> image_url`, NOT in the `image_urls` column, which is `[]` on every row — and `project_purchase_items.design_image_url`, the product shot the purchase spec-sheet PDF embeds. Eight live objects under `generation-images/gemini/` were six days from the 14-day reaper with nothing in the reference set claiming them. Both registered; the probe now has a second arm that samples `%url%` / jsonb / array columns for `/storage/v1/object/` in live data and reports only what it can prove (name alone cannot separate `design_image_url` from `virtual_tour_url`). **And the registration check itself had a blind spot in the opposite direction to the one it documents:** `strpos(def, 'public.' || tbl)` was qualified so `documents` could not satisfy `hr_documents` — but `generation_3d` is a PREFIX of `generation_3d_segments`, which has been registered for months, so it read as covered while it was not. Now `\M`-anchored at both ends. Watched to fire: with the branch cut back out inside an aborted subtransaction the set loses all 16 `gemini/` rows and the probe names `generation_3d.models_results`.
- **`credit_transactions.metadata` is exempt on purpose.** It quotes the source image of a past generation as billing evidence; it does not own the file (`vr_worlds` / `generation_3d` do, and both are registered), and the table has no TTL by design — registering it would pin every source image forever. A ledger mentioning a URL is not a claim on it.
- **Sheet images live in jsonb, and are protected by a URL scan, not a column.** `moodboard_presentation_sheets.data` holds every uploaded image a sheet uses (`backdrop.image_url`, `backdrop_image_url`, `elevation_image_url`, `render_image_url`, `layout[].image_url`, cover images) — all written to `generation-images/u/{uid}/sheet-uploads/` by `SheetWizardModal`. The table's `pdf_storage_path` entry does **not** cover them, so `build_storage_reference_set()` regex-scans `data::text` the same way it scans agent chat messages. Added 2026-08-04 after finding they would be reaped at the 14-day grace while still referenced. **The pattern stops at `"`, `?`, whitespace and `)`** — an audit of other jsonb columns found `agent_checkpoints` stores markdown, where a URL inside prose ran past its end and captured `…png)\n\nThe design features…` as the object path. That fails in the dangerous direction: a junk path protects nothing, so the real file drops out of the set and gets deleted.
- **Project site photos (#358 PQ-9):** snag + site-log photos are `pdf-documents` object paths under `project-site/project-snags/{project_id}/{user_id}/…` and `project-site/project-site-logs/{project_id}/{user_id}/…`, read through `createSignedUrls` (1h). They were in `generation-images` and rendered with `getPublicUrl()` until 2026-08-17 — a defect photo of the inside of a client's home, and the site log that is internal-only with no collaborator read policy at all, openable by anyone holding the URL with no session. `siteService.uploadPhotos` validates MIME + size (15 MB) before the upload. Both arrays are registered in `build_storage_reference_set()` against the NEW bucket; the branch hardcodes it, so a future move has to change both.
- **Project covers (2026-09-05):** `projects.cover_image_url` is a URL — an upload under `generation-images/u/{user_id}/project-covers/{project_id}/`, or an AI render copied off the `generate-interior-gemini` result (which `generation_3d` also claims). Registered in `build_storage_reference_set()` through `_extract_storage_*_from_url`, matched only when it is an absolute `http(s)` URL: a LIBRARY cover is a site-relative path (`/covers/projects/kitchen.webp`, a static app asset) and is not a storage claim. Upload and render are `projectsService.uploadCoverImage` / `generateCoverImage`; the URL is persisted only on confirm in `ProjectCoverDialog`, so an unchosen render lives on as ordinary generation history.
- **Room floor plans:** `project_rooms.plan_storage_bucket` + `plan_storage_path` hold the MEP plan backdrop (`generation-images`, under `u/{user_id}/room-plans/{room_id}/`). A CHECK keeps the pair set together — half a reference is both unreadable *and* invisible to the GC, which is precisely the state that gets a live file deleted.
- **Product 3D models (#321):** `product_3d_models.storage_bucket` + `storage_path` (`generation-images`, `3d/{product_id}/…`, one row per product×format) are registered in `build_storage_reference_set()`. Replacing a format upserts the row to the new path; the old file drops out of the reference set and the 14-day grace reaps it — deliberate, no explicit delete needed. `product3dService.deleteModel` removes row first, then best-effort `storage.remove()`, with the cron as backstop.

**Per-session agent layout (2026-05-31 reorg):** everything a chat creates now lives under one per-session prefix in `generation-images` so deleting the chat deletes one folder. Canonical layout (built by `_shared/storage-paths.ts` on the edge + `src/utils/storagePaths.ts` on the client):
- `u/{user_id}/sessions/{conversation_id}/gen/{job}.{ext}` — AI generations (gemini, region-edit, virtual-staging, video-v2). Each generation edge function takes optional `conversation_id` in its body and `resolveOutputPath(ctx, '<legacyPrefix>', file)` falls back to the legacy flat prefix when absent → **safe partial rollout**. `user_id` is derived server-side from the bearer, never path-built from the body. PBR maps (`pbr-maps/{productId}/`) and social images (`social/`) are intentionally NOT session-scoped — they're entity-scoped assets with their own lifecycle.
- `u/{user_id}/sessions/{conversation_id}/uploads/{ts}-{n}.{ext}` — user-attached chat images. AgentHub creates the conversation **before** uploading so first-message attachments land in the session folder (not the legacy `user-uploads/` prefix).
- `u/{user_id}/moodboards/{moodboard_id}/{item_id}.{ext}` — **copy-on-promote** target. `moodboardAPI.addMediaFromChat()` `.copy()`s the bytes here (original stays in the chat) so the image survives chat deletion. `MoodboardSavePopover` calls it instead of storing the raw session URL.
- **Cleanup:** `_cleanup_session_storage` (AFTER DELETE on `agent_chat_conversations`) prefix-deletes `u/{uid}/sessions/{cid}/`. The legacy regex scrubbers (`_cleanup_chat_message_storage` / `_cleanup_conversation_storage`) stay as forward-only transition belt-and-braces for pre-reorg objects (their paths carry no conversation linkage so they can't be migrated). `build_storage_reference_set` gained an `is_prefix=true` row per **live** conversation, so a session image is protected by the conversation's existence — not by its URL being embedded in a message (closes the gemini-intermediate / edited-away-attachment reap gap).
- **Catalog rebuild cleanup:** `generate-catalog-pdf` clears the `catalog-output/{catalog_id}/` prefix before each rebuild (was accumulating timestamped PDFs). `_cleanup_catalog_output_storage` (AFTER DELETE on `presentation_catalogs`) clears the output prefix; `_cleanup_catalog_source_pdf_storage` (AFTER DELETE on `catalog_source_pdfs`) removes the source PDF + its `pdf-tiles/catalog-extracted/{source_pdf_id}/` tiles. Source PDFs stay keyed by `source_pdf_id` (uploaded into a library before any catalog exists, so they're not catalog-keyed).
